# Media, preview, settings, and cloud integration

## Export without transcoding

DIGA exports **original encoded streams**. FFmpeg always receives `-c copy`. It never substitutes a video/audio encoder to force a container to work. MKV is the default for Panasonic MPEG-2/AC-3 material. MPEG output is an MPEG program stream (`.mpg`), restricted to original MPEG-2 video with supported original audio. MP4 accepts compatible original codecs such as H.264/H.265 video and AAC/AC-3 audio. Choosing MP4 does not turn MPEG-2 video into MPEG-4 video.

FFprobe inspects every stream first. All original video, audio, and subtitle streams must be compatible; incompatible streams produce a clear error instead of being silently removed. Recorder private/control `data` streams are excluded explicitly. Some broadcast subtitles, especially DVB subtitles, cannot be copied to these containers and therefore prevent export. A future explicit track-selection workflow can let a user choose how to handle such material.

The media services accept a staged local file from the read-only storage layer. The original disk is never passed to FFmpeg as an output. Arguments use `ProcessStartInfo.ArgumentList`, and local media input is limited to the `file` and `pipe` protocols. Exports use a unique temporary file in the destination folder, re-probe its codecs and stream count, then move it to the final filename without overwriting. Cancellation terminates the process tree and deletes partial output. A disk-full or FFmpeg error retains the original source and never publishes a partial final file.

The first 45 seconds of the first video/audio tracks can be copied to a unique MKV preview file. Export still preserves all compatible media tracks. Embedded playback uses Windows media components: MPEG-2/AC-3/HEVC playback may need a suitable Windows codec extension, depending on the installed OS version. An inability to play a preview does not imply an inability to export the recording. Preview is not a transcoding fallback. Storage staging may take time and needs local free space.

Native MediaInfo is loaded through its C ABI from the configured x64 `MediaInfo.dll`. A separate native handle is allocated for each inspection. JSON output is available for source and destination; missing/wrong-architecture DLLs return a clear dependency error. MediaInfo's network option is disabled. The native call is synchronous internally, so cancellation is observed before/after the native file scan rather than interrupting an in-progress unmanaged scan.

## Tool locations and settings

The ordinary JSON settings file defaults to `%LOCALAPPDATA%\Diga\settings.json`. It contains output/cache folders, the three media tool paths, preferred container, wizard preference, and, only if the user entered one, their own Microsoft application (client) ID; the field is empty when the built-in ID is used. A Google client ID saved by version 0.5.0 or earlier stays in the file and is used only at startup, each time the app starts, to remove a Google sign-in saved under it (see below). Writes use a temporary file and an atomic replace. Invalid/corrupt settings are preserved and reported. Cloud access and refresh tokens are **not** written to this JSON file.

Tool defaults look for application-relative `tools`, application-relative `tools\bin`, then development `tools\bin` in the current directory. A PATH executable name is the final fallback. For a development checkout, run the repository's dependency bootstrap and set paths explicitly if launching from another working directory.

## Cloud destination

From version 0.5.1 the application uploads to **OneDrive only**; the Google Drive option was removed from **Archive** and **Settings**. The core library still contains the Google Drive upload code and its tests, but the application does not call it.

The upload is written for both personal OneDrive (a `live.com`, `outlook.com` or `hotmail.com` Microsoft account) and work/school OneDrive, through one application registration that is open to personal Microsoft accounts. **Sign-in and upload have been reported working by the project owner; the project's own tests have not run them**: On 2026-10-02 the project owner reported that **Connect OneDrive** and an upload from **Archive** in version 0.5.2 worked with their Microsoft account. The project's own tests had no Microsoft account, so apart from that report and the checks below, the statements here rest on Microsoft's documentation and published reports. The app signs in through the `common` Microsoft endpoint as a public client with PKCE, so **no client secret is needed or used**.

From version 0.5.2 the application (client) ID of the project owner's Microsoft registration, `aa6acb80-dd42-45d3-b260-e44f327c4c42`, is built in, so nothing has to be entered in Settings: choose **Settings → Microsoft OneDrive → Connect OneDrive** and sign in. The ID is an identifier, not a credential; it tells Microsoft which registered application is asking, and each user still signs in to their own account and approves access to their own files. The field **Your own application ID (optional)** stays for anyone who prefers their own registration; leaving it empty uses the built-in ID.

What Microsoft's sign-in service answered for the built-in ID on 2026-10-02, without signing in: the personal-account endpoint showed its sign-in page for this ID with a `http://localhost:<port>` redirect, refused the same ID with a different redirect (`invalid_request`) and refused an unknown ID ("not enabled for consumers"). So the registration exists, is open to personal accounts and accepts the loopback redirect (one port was tried; Microsoft documents that the port is ignored). These checks ran on the personal-account endpoint (`consumers`), while the app signs in through `common`, which answers the same way whatever is asked before sign-in. `common` needs the registration's **Supported account types** to be **Any Entra ID Tenant + Personal Microsoft accounts**; that value cannot be read from outside. The project owner states that this is the value chosen for the registration (the organizations endpoint did accept the ID, which fits it); it has not been confirmed by a sign-in. If the first sign-in ends on Microsoft's page with `AADSTS9002331` ("configured for use by Microsoft Account users only"), the registration is set to personal accounts only: change the supported account types in the Entra admin center. At that point the sign-in itself, the consent, the token exchange and an upload had not been run; the owner's later report of a working connection and upload covers all four, and with them the account-type setting and the redirect registration.

Also from 0.5.2: when Microsoft's message carries its trace and timestamp text on the same line as the reason, as its token endpoint did in these checks, the app shows only the part before that text.

What was adapted for personal accounts in 0.5.1, from documentation and reports rather than from a live run:

- Upload addresses on `my.microsoftpersonalcontent.com`, which Microsoft returns for some personal accounts, are accepted (others use `api.onedrive.com`, which was already accepted).
- Sign-in always shows Microsoft's account chooser (`prompt=select_account`). Without it Microsoft signs in the browser's only current account, which on a work PC is usually the work account.
- After sign-in the app asks Microsoft Graph which drive it reached and shows it in **Settings** and **Archive**, for example **Connected · OneDrive (personal) · owner name**. If that question fails, is not answered within 15 seconds or returns something unreadable, the connection still works and the label is just **OneDrive**. A sign-in saved before 0.5.1 shows **OneDrive** until it is connected again.
- When Microsoft refuses a sign-in or an upload, or keeps answering an upload with a server or throttling error until the retries run out, the error code and first line of Microsoft's message are shown after the app's own text. Only those named fields are read; the rest of the response is never shown.
- If the local port chosen for the sign-in reply is already in use, another one is tried. Earlier versions failed with a "disposed object" error in that case.
- The redirect address is sent as `http://localhost:<port>` without a trailing slash, the form Microsoft's own libraries send.

## OneDrive registration

This section is needed only for a registration of your own; the built-in application ID needs none of it. An application registration identifies this desktop application to Microsoft. It is created once and is separate from the OneDrive account files are uploaded to; the same personal account can own both.

**Before step 1:** Microsoft lists an Azure account and a directory (tenant) as [prerequisites for registering an application](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app). A personal Microsoft account that has no directory is refused with a message that creating applications outside a directory is no longer possible. Such an account gets a directory ("Default Directory") by signing up for a free Azure account, which asks for identity verification (phone and payment card, according to published reports); the registration is then created in that directory. The project has not gone through this path itself.

The portal labels below follow Microsoft's documentation as read on 2026-10-02; the portal itself was not inspected, and older layouts use the names in brackets.

1. Open [Microsoft Entra admin center](https://entra.microsoft.com/), then **Entra ID → App registrations → New registration** (older layout: **Identity → Applications → App registrations**).
2. Enter an application name. Under **Supported account types** choose **Any Entra ID Tenant + Personal Microsoft accounts** (older label: **Accounts in any organizational directory and personal Microsoft accounts**). This choice is required: a single-tenant or organizations-only registration cannot be used with the `common` endpoint for a personal account. Leave the redirect URI empty here and register.
3. Copy **Application (client) ID** from the overview page into the app: **Settings → Microsoft OneDrive → Your own application ID (optional)**.
4. Open **Authentication**, choose **Add Redirect URI** on the **Redirect URI configuration** tab (older layout: **Add a platform**), select **Mobile and desktop applications**, enter `http://localhost` as a custom redirect URI and choose **Configure**. Microsoft ignores the port of a `localhost` redirect, so the app can listen on a free port. Do not add it under **Web** or **Single-page application**, and do not create a client secret. Leave **Allow public client flows** at its default (**No**): Microsoft's [public client flows](https://learn.microsoft.com/en-us/entra/identity-platform/msal-client-applications) page says to keep it disabled unless the app uses device-code, resource-owner password or integrated Windows sign-in (or Native Authentication), and this app uses none of them. This has not been checked against Microsoft, and one sentence on Microsoft's loopback redirect page reads as if the setting were needed whenever a redirect URI is registered; see the fallback below.
5. Optional: under **API permissions** add the Microsoft Graph **delegated** permission `Files.ReadWrite`. The app requests it (with `offline_access`) at sign-in, so a personal account is asked for consent either way. It does not use application permissions or a service account. An organization may require administrator consent according to its own policy.
6. In the app choose **Save preferences**, then **Connect OneDrive**. Pick the account in the browser and accept the permission request. After a local export, check the copies in **Archive** and choose **Upload selected copies**; files go to the root of the drive. Existing cloud files are preserved by OneDrive's `rename` conflict behavior.

If the first sign-in fails, Microsoft's message names the cause, on Microsoft's own page or after the app's text:

- `AADSTS50011`: the redirect address does not match the registration (step 4), per Microsoft's [error reference](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes).
- `AADSTS50194`: the registration is not multitenant, so it cannot be used with the `common` endpoint (step 2), per the same reference.
- `AADSTS7000218` (a client secret or assertion is demanded): Microsoft's [troubleshooting article](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/confidential-client-application-authentication-error-aadsts7000218) explains that a redirect of type **Web** makes the registration a confidential client; move it to **Mobile and desktop applications** (step 4). Untested fallback if it appears although the only `http://localhost` redirect is already there: set **Allow public client flows** to **Yes** and try again.
- `unauthorized_client` or `AADSTS700016`: per the error reference, the application is not registered or the ID was not found; first check the application ID pasted in step 3 (or clear the field to return to the built-in ID). Published reports also show `unauthorized_client` for a registration that is not open to personal accounts (step 2).

Official guidance: [Register an application](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app), [Add a redirect URI](https://learn.microsoft.com/en-us/entra/identity-platform/how-to-add-redirect-uri), [Native authorization code flow with PKCE](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [Loopback redirect rules](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url), [Public client flows](https://learn.microsoft.com/en-us/entra/identity-platform/msal-client-applications), [Error reference](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes), [Graph upload sessions](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0).
## Upload and credential behavior

Connecting and uploading are separate user actions. Cloud service constructors/settings loading do not contact a cloud provider. Authentication starts a local browser flow only when `AuthenticateAsync` is called. The local listener is bound to localhost, validates a random OAuth state, uses a new PKCE verifier/challenge, and times out after five minutes. OAuth callback errors and token endpoint failures do not log credentials.

Tokens are protected with Windows DPAPI for the current user and saved under `%LOCALAPPDATA%\Diga\Accounts`, one file per application ID. A Windows account change cannot decrypt them. **Disconnect** removes the local token file and saves the settings on the page (if the page cannot be saved, for example because a folder field is empty, the sign-in is still removed and the app says the page was not saved); changing the application ID and saving removes the sign-in saved for the previous ID before the new ID is stored. Neither revokes consent at Microsoft: to revoke it, use the Microsoft account's page of apps and services that have access.

A Google Drive sign-in saved by version 0.5.0 or earlier is removed at startup: the app deletes the token file for the Google client ID still present in `settings.json`. A token saved under a different, earlier Google client ID is not found this way; delete `GoogleDrive-*.bin` in `%LOCALAPPDATA%\Diga\Accounts` by hand. Deleting the file does not revoke consent at Google; revoke it in the Google account's third-party access page. Uninstalling does not remove the `Accounts` folder. Access tokens refresh on explicit upload when near expiry. DPAPI encryption is not a substitute for Windows account/device security.

Uploads use 5 MiB chunks, a multiple of Microsoft's 320 KiB requirement. DIGA uses provider acknowledgements for offsets. After a transient failure (a lost connection, a request timeout, HTTP 429 or 5xx) it waits, asks the provider how much it holds and continues from there; the status question is retried in the same way. Up to five consecutive failures are tolerated, with waits of 2, 4, 8, 16 and 30 seconds unless the provider names a delay (bounded to 1–30 seconds), so an interruption longer than about a minute ends the upload. An acknowledged chunk resets the count. When the retries run out on a server or throttling answer, the message carries the HTTP status and the provider's reason, for example a full drive. If the provider answers the status question after a failure with "not found", the app says the session is lost and asks you to check the drive before uploading again, because the file may already be complete; a "not found" answer to a chunk itself is reported as a failed chunk with the provider's message. Cancellation is honoured during waits. OneDrive's preauthorized chunk URL receives no Authorization header. Session URLs must be HTTPS and on recognized provider hosts, and default HTTP clients do not follow redirects. A local file remains open read-only and cannot be modified by another ordinary writer during transfer.

Resuming is currently limited to a running upload operation. Upload-session state is not persisted across application restarts. Cancelled/incomplete remote sessions expire according to provider policy. Cloud names are validated and existing cloud files are not overwritten. An upload should be treated as successful only after the provider returns the completed file identifier.

## Validation and practical limits

The automated suite exercises codec/container rejection, all-media stream mapping, atomic publication, preservation of source/existing output, failed/cancelled partial cleanup, probe parsing, missing MediaInfo, settings round-trip/concurrency/corruption, the RFC PKCE challenge vector, real localhost callback state validation, DPAPI round-trip, token refresh, provider host validation, both chunk protocols, rejected byte ranges, transient retry/resume including a failed status query, the retry limit with the provider's reason and a lost session, the OneDrive account chooser and drive label including an unanswered or unreadable drive answer, a busy sign-in port, and provider error details that exclude other response fields.

The repository's integration suite separately invokes the actual FFmpeg/FFprobe and native MediaInfo libraries with generated media. Those fixture encoders are test-only; product exports never encode. No Microsoft account was available for the project's tests. The owner reported a working sign-in and upload with 0.5.2, without details of the account type or file size; tenant policies, quota behavior, interrupted uploads and work/school accounts remain unverified. No physical Panasonic disk was supplied; codec/encryption behavior of a user's recordings must be checked against actual hardware. The application cannot decrypt recordings protected by the recorder.
